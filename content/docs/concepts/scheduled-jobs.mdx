---
title: Scheduled jobs
description: Run a job at a later time with at, or push jobs on a cron schedule.
---

Anway has two ways to run work later:

- **`at`:** push one job now, and the server runs it at the time that you give.
- **Cron:** the server pushes a job on a repeating schedule, from its YAML settings or from the cron that your app declares.

## Run a job later

<Tabs items={['Ruby', 'Go', 'Node.js']}>
<Tab value="Ruby">

```ruby
ReminderJob.perform_in(300, user.id)
ReminderJob.perform_at(Time.now + 3600, user.id)

Anway.push('reminder.send', [user.id], at: Time.now + 3600)
```

</Tab>
<Tab value="Go">

```go
job, err := anway.NewJob("reminder.send", []any{user.ID}, anway.Options{
	At: time.Now().Add(time.Hour),
})
if err != nil {
	return err
}

return client.Push(ctx, job)
```

</Tab>
<Tab value="Node.js">

```ts
const at = new Date(Date.now() + 60 * 60 * 1000);

await client.push(new Anway.Job('reminder.send', [user.id], { at }));
```

</Tab>
</Tabs>

- In Ruby, `perform_in` takes seconds, and `perform_at` takes a time. `set(at: ...)` also works.
- In Go, `job.RunAt(t)` sets the time on a job that you already made.
- `at` is only for a push. A worker declaration does not take it.

### How it works

1. The client sends `at` as an RFC 3339 time.
2. A job with a future `at` goes to the Scheduled set, not to its queue.
3. The server checks the Scheduled set about once per second. When the time arrives, it moves the job to the end of its queue.
4. A worker then fetches the job as usual.

A job with an `at` in the past, or with no `at`, goes to its queue at once. The time is the earliest run time, not an exact time: the job can wait in its queue after that time, for example behind other jobs.

A scheduled job is on disk, as any job. It survives a server restart.

### Change scheduled jobs

Use `mutate` with the `scheduled` target. `requeue` runs the jobs now, `kill` moves them to the Dead set, and `discard` deletes them. See [Retries](/docs/concepts/retries#run-kill-or-discard-jobs).

<Tabs items={['Ruby', 'Go', 'Node.js']}>
<Tab value="Ruby">

```ruby
Anway.client.mutate('requeue', 'scheduled', event: 'reminder.send')
```

</Tab>
<Tab value="Go">

```go
return client.Mutate(ctx, "requeue", "scheduled", anway.Filter{Event: "reminder.send"})
```

</Tab>
<Tab value="Node.js">

```ts
await client.mutate('requeue', 'scheduled', { event: 'reminder.send' });
```

</Tab>
</Tabs>

The **Jobs** page of the web console also lists the scheduled jobs.

## Cron

The server pushes cron jobs itself. You do not need a client process for the schedule. Add the entries to a YAML file in the server `CONF_DIR`:

```yaml title="conf.d/cron.yml"
cron:
  - schedule: "*/5 * * * *"
    job:
      type: Cleanup
      queue: ops
      retry: 3
      args: [1]
      custom:
        expires_in: 60
```

| Key | Meaning |
|---|---|
| `schedule` | A standard cron expression with five fields: minute, hour, day of the month, month, day of the week. |
| `job.type` | The job type. Required. |
| `job.queue` | The queue. The default is `default`. |
| `job.args` | The args. The default is `[]`. |
| `job.retry` | The retries. The default is the server default, 25. |
| `job.reserve_for` | The reservation in seconds. |
| `job.custom` | The custom hash, for example `expires_in`. |

- Schedules use UTC.
- A time that the server missed while it was down does not run later.
- With more than one server, each server pushes the job.
- An unknown key or a bad schedule is an error. At boot, an invalid file stops the server.
- `SIGHUP` reloads the files. If a file is invalid, the old settings stay active.

The example uses `expires_in: 60`. If its job waits more than 60 seconds in the queue, the server discards it at fetch. See [Expiring jobs](/docs/concepts/unique-jobs#expiring-jobs).

The **Schedules** page of the [web console](/docs/server/console) shows each cron entry, with its job, queue, source, and the time of the next run. See [Configuration](/docs/server/configuration) for `CONF_DIR`.

## Schedules from the app

Since 0.6.0, your app can declare its cron in its own code or config, as Solid Queue recurring tasks do. You do not need access to the server files, so this also works on Anway Cloud. The worker sends the entries to the server when it starts, and the server keeps them on disk.

<Tabs items={['Ruby', 'Go']}>
<Tab value="Ruby">

```ruby
class RefillCredits
  include Anway::Worker

  anway_options event: 'credits.refill', queue: 'default', retry: 3, cron: '0 0 * * *'

  def perform
    # ...
  end
end
```

Or in `config/anway.yml`, with the same keys as a server YAML file:

```yaml title="config/anway.yml"
tag: shop

cron:
  - schedule: "0 6 * * *"
    job:
      type: report.daily
      queue: reports
      args: [7]
```

`cron` takes a string or an array of strings. The worker sends the entries of the job classes and of the file together.

</Tab>
<Tab value="Go">

```go
worker := anway.NewWorker("", anway.WorkerOptions{Tag: "shop"})

worker.On("credits.refill", refill, anway.Options{
	Queue: "default",
	Retry: anway.Int(3),
	Cron:  []string{"0 0 * * *"},
})

return worker.Run(ctx)
```

</Tab>
</Tabs>

- Each schedule makes one cron entry. Its job has the event as its type, and the queue, retry, and reserve_for of the declaration.
- The entries belong to the **tag** of the app, such as `shop`. A worker with cron entries and no tag does not start. In Ruby, set `tag` in `config/anway.yml`, `ANWAY_TAG`, or `--tag`. In Go, set `WorkerOptions.Tag`.
- At each start, the worker sends all its entries in one `SCHEDULE`. The server replaces all entries of the tag, so an entry that you remove from the code goes away.
- A worker with no cron entries sends nothing. To remove the last entry of a tag, call `unschedule` once.
- All processes with one tag must declare the same entries, because the last `SCHEDULE` wins.
- A bad schedule, or an entry with no job type, is an error, and the entries on the server do not change.
- The server runs the entries of its YAML files and of all tags together. `SIGHUP` reloads only the YAML files.
- The entries stay after a server restart, and they do not need a connected worker.

You can also change the entries of a tag from any process, such as the Rails console or a deploy script:

<Tabs items={['Ruby', 'Go']}>
<Tab value="Ruby">

```ruby
Anway.schedule('shop', [{ schedule: '0 0 * * *', job: { type: 'credits.refill', queue: 'default' } }])
Anway.unschedule('shop')
Anway.cron # the entries that the worker of this app sends at start
```

</Tab>
<Tab value="Go">

```go
err := client.Schedule(ctx, "shop", []anway.CronEntry{
	{Schedule: "0 0 * * *", Job: anway.CronJob{Event: "credits.refill", Queue: "default"}},
})

err = client.Unschedule(ctx, "shop")
```

</Tab>
</Tabs>

The **Schedules** page of the web console shows `conf.d` for an entry of a server YAML file, and the tag for an entry of an app. `GET /api/v1/schedules` has the same `source` and `tag`.

<Callout type="info" title="Moving from Solid Queue">
Move each task of Rails `recurring.yml` to `anway_options cron:` in its job class, or to the `cron` key of `config/anway.yml`.
</Callout>
